이 문서는 로컬 GitHub 로그인으로 접근 가능한 Coreline GitHub 저장소의 `README.md`와 `dev-plan/**/*.md`만 선택적으로 수집·파싱해 AI Systems Atlas 지식 그래프에 적용하는 개발 범위를 고정하고, 구현이 목적 밖으로 확장되지 않도록 하기 위한 작업 문서다.

## 개발 목적

로컬 `gh auth`로 `coreline-ai` 계정에서 접근 가능한 공개·비공개 저장소를 탐색하고, 사용자가 선택한 저장소의 기본 브랜치에서 루트 `README.md`와 `dev-plan` 디렉터리 아래 모든 `.md` 파일만 저장소 단위로 동기화한다. README에서는 프로젝트 목적·기능·기술을, 개발 계획에서는 Phase·작업·완료 상태·위험·의존성을 추출하고, 모든 관계가 GitHub 원문과 Markdown 블록 근거를 유지하도록 한다. GitHub 자격 증명은 로컬 Connector의 `gh` 프로세스 밖으로 전달하거나 웹앱·D1에 저장하지 않는다.

## 개발 범위

- 로컬 Connector가 기존 `gh auth` 로그인으로 `coreline-ai`에서 현재 사용자에게 보이는 공개·비공개 저장소를 조회한다.
- 저장소 개수는 고정하지 않고 매 discovery 응답을 정본으로 사용한다. 계획 수정 시점의 사용자 화면 기준치는 117개, 공개 프로필 API 기준치는 78개다.
- discovery 결과에서 공개·비공개, fork, archived, template, 기본 브랜치, 최근 갱신 시각을 표시하고 실제 동기화 대상은 사용자가 선택한다.
- 각 저장소 기본 브랜치의 루트 `README.md`와 `dev-plan/**/*.md` 일반 파일을 최소 수집 대상으로 삼는다.
- 테스트로 추정되는 저장소는 이름만으로 자동 제외하지 않고 경고 배지와 사용자 선택으로 처리한다.
- GitHub 저장소 숫자 ID와 상대 경로를 기반으로 충돌하지 않는 문서 식별자를 도입한다.
- 저장소·경로·브랜치·커밋·Blob SHA·원본 URL을 문서 메타데이터로 저장한다.
- README 전용 추출과 dev-plan 전용 Phase·체크박스 작업 추출을 기존 Markdown AST 파이프라인에 연결한다.
- 저장소 하나의 대상 문서를 모두 검증한 후에만 기존 그래프를 교체하는 저장소 단위 동기화를 구현한다.
- 사용자가 선택한 저장소의 대상 문서는 모두 저장하되 그래프 화면은 전체 저장소 개요와 선택 저장소 상세의 2단계 투영을 제공한다.
- 대시보드에서 Connector·GitHub 로그인 상태, 저장소 선택, dry-run 결과, 저장소별 동기화 상태, 실패 원인, 마지막 동기화 시각과 원본 링크를 확인한다.
- 최초 전체 동기화와 이후 Blob SHA 기반 증분 동기화를 지원한다.

## 문서 기반 제약 사항

- 현재 `documents.normalized_name`은 전역 UNIQUE이므로 여러 저장소의 `README.md`가 충돌한다.
- 현재 문서 ID도 파일명에서 파생되므로 GitHub 문서에는 별도 source key 계약이 필요하다.
- 현재 일반 Markdown 추출기는 dev-plan의 Phase·체크박스 완료 상태를 구조화하지 않는다.
- 현재 업로드 API는 한 번에 최대 20개 파일이므로 GitHub 전체 동기화는 저장소 단위 staging과 전용 작업 API가 필요하다.
- 현재 성능 기준은 500노드·2,000관계이므로 전체 문서를 단일 GraphSnapshot으로 투영하지 않는다.
- 공개 프로필 API의 `public_repos`는 78개지만 로그인된 사용자 화면에는 117개 저장소가 보인다. 이 숫자는 계획 상수가 아니며 Connector discovery 결과를 정본으로 사용한다.
- Cloudflare 웹 런타임은 로컬 `gh` 자격 증명 저장소와 프로세스에 접근할 수 없으므로 GitHub 탐색·다운로드는 로컬 Connector가 담당해야 한다.
- 원격 Markdown은 신뢰할 수 없는 입력이다. 파서는 데이터로만 처리하고 Codex 보강에서도 문서 내부 지시문을 실행하지 않는다.

## 결정 기록

### 실행 경계 계약

- 웹앱은 GitHub 자격 증명을 직접 받지 않고 보호된 작업 API를 통해 discovery·preview·apply 작업만 생성한다.
- 기존 로컬 Connector에 `github-source` capability를 추가하고 Codex 보강 작업과 GitHub source 작업의 큐·상태·오류 코드를 분리한다.
- Connector는 실행 전에 `gh auth status`와 대상 계정 접근을 확인하고 `online`, `login_required`, `forbidden`, `rate_limited`, `offline` 상태를 보고한다.
- Connector는 `gh repo list`와 `gh api`를 사용하되 토큰 값, Authorization 헤더, 전체 명령 환경을 결과·로그·D1에 포함하지 않는다.
- 공개 저장소 비인증 REST 수집 경로를 별도로 중복 구현하지 않는다. 향후 Connector 없는 공개 읽기가 필요하면 별도 범위로 검토한다.
- Codex 보강은 기존 `codex login`을, GitHub 수집은 기존 `gh auth`를 각각 사용하며 두 인증 상태와 실패 원인을 혼합하지 않는다.

### 저장소 선택 계약

- discovery는 현재 로그인 사용자에게 보이는 `coreline-ai` 소유 저장소를 누락 없이 반환하며 숫자 117을 코드 상수로 사용하지 않는다.
- UI는 공개·비공개, fork, archived, template, 최근 갱신 시각을 배지와 필터로 제공한다.
- 기본 추천 선택은 `owner 일치 + archived 아님 + fork 아님`이며 비공개 저장소도 권한이 있으면 포함한다.
- 테스트·실험 저장소로 보이는 이름은 경고만 표시하고 자동 제외하지 않는다.
- 사용자가 확정한 저장소별 `sync_enabled`만 저장하며 선택 전 discovery·preview는 문서·그래프 데이터를 변경하지 않는다.
- 이전에 동기화한 저장소가 discovery에서 보이지 않으면 즉시 삭제하지 않고 `inaccessible`로 표시해 재로그인·권한 복구 후 다시 판단한다.

### 수집 대상 계약

- 포함: 저장소 루트의 정확한 경로 `README.md`
- 포함: `dev-plan/` 아래 재귀적으로 발견한 확장자 `.md` 일반 Blob
- 제외: 다른 디렉터리의 README, `.mdx`, symlink, submodule, 디렉터리 엔트리, 2MB 초과 파일
- README가 없어도 dev-plan 문서가 있으면 해당 저장소는 동기화한다.
- 재귀 Tree 응답이 `truncated=true`이면 Contents API 디렉터리 순회로 대체하고, 대체 탐색도 실패하면 해당 저장소를 변경하지 않는다.
- 파일 목록과 Blob 다운로드는 Connector가 수행하고, 서버에는 허용 경로·크기·UTF-8 검증을 통과한 manifest와 Markdown만 전달한다.
- Connector 결과는 저장소 단위로 청크 전송할 수 있지만 서버 commit은 해당 저장소의 모든 대상 문서 검증 성공 후 한 번만 수행한다.

### 식별자 계약

- 저장소 식별자: `github-repo:<github_repository_id>`
- 문서 source key: `github:<github_repository_id>:<case-sensitive-relative-path>`
- 문서 ID는 source key의 충돌 저항 해시로 만들고 브랜치·커밋 SHA를 포함하지 않는다.
- 기존 수동 문서는 연결된 block·mention·relation·작업을 보존하기 위해 기존 문서 ID를 유지하고 source key만 backfill한다. 신규 수동·GitHub 문서부터 SHA-256 문서 ID를 사용한다.
- 저장소명 변경은 동일 GitHub 숫자 ID로 갱신하고, 경로 변경은 새 문서 생성과 이전 문서 stale 처리로 다룬다.
- 저장소·문서·섹션·Phase·Task 노드는 source-local ID를 사용한다.
- 언어·프레임워크·제품명·명시적 외부 링크처럼 정규화 가능한 엔티티만 저장소 간 전역 공유한다.

### 그래프 투영 계약

- `overview`: 저장소 노드와 공유 기술·명시적 저장소 간 관계를 중심으로 500노드 예산을 지킨다.
- `repository`: 선택한 저장소의 README 섹션, 계획 문서, Phase, Task와 근거 관계를 상세 투영한다.
- 추가 관계 종류는 `documents`, `plans`, `contains`로 제한하고 기존 `uses`, `requires`, `risks`, `supports`, `extends`를 재사용한다.
- 모든 규칙·Codex 관계는 document block과 GitHub source URL을 추적할 수 있어야 한다.

### 보강 계약

- 최초 전체 동기화는 규칙 기반 파싱 결과를 먼저 커밋한다.
- bulk 수집 중에는 문서별 Codex 보강 작업을 즉시 생성하지 않는다.
- 저장소 동기화 성공 후 변경 문서만 보강 큐에 넣을 수 있도록 명시적 옵션을 둔다.
- 보강 실패는 규칙 기반 그래프와 GitHub 동기화 성공을 롤백하지 않는다.
- GitHub Markdown은 보강 프롬프트에서 명령이 아닌 인용 데이터로 경계화하고, Connector는 스키마에 맞는 관계 결과만 반환하며 문서가 요구하는 도구 호출을 실행하지 않는다.

### 작업 API·권한 계약

- discovery·preview·apply·retry·cancel은 모두 현재 보호된 쓰기 정책과 Connector 인증을 통과해야 한다.
- 브라우저는 discovery/apply 작업 ID와 정제된 상태만 받고 GitHub 토큰·인증 헤더·비공개 원문을 직접 받지 않는다.
- `preview`도 GitHub 요청과 로컬 Connector 자원을 소비하므로 공개 무제한 API로 제공하지 않는다.
- apply는 선택 저장소와 직전 preview manifest digest를 함께 받아 오래된 preview를 적용하지 않는다.
- 같은 저장소의 동시 apply는 lease와 idempotency key로 한 실행만 허용하고 만료된 lease의 복구 규칙을 둔다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- GitHub 원격 응답과 기존 D1 데이터 변경은 dry-run 결과 확인 후 분리해 실행한다.
- 저장소 하나에서 일부 문서가 실패하면 해당 저장소의 기존 정상 그래프를 유지한다.
- 외부 요청에는 timeout·페이지네이션·제한된 재시도를 적용하고 응답 본문이나 인증 정보를 로그에 남기지 않는다.
- `403`·`429`에서는 무조건 반복 재시도하지 않고 `Retry-After`·rate limit reset을 상태에 기록해 사용자가 재시도 시점을 알 수 있게 한다.
- 기존 `ingestMarkdown`, staging 저장, Connector 계약을 확장하되 별도 중복 파이프라인을 만들지 않는다.
- 새 의존성 없이 표준 `fetch`, 현재 Remark·D1·React 구조를 우선 사용한다.
- 정식 D1 변경은 새 migration 파일로 작성하고 런타임 `ensureSchema`와 동일한 계약을 유지한다.
- 운영 배포와 운영 마이그레이션은 별도 사용자 승인 전까지 실행하지 않는다.
- 각 Phase 내부도 하나의 검토 가능한 증분 단위로 구현하고, 사용자 결과 확인 전 다음 증분으로 넘어가지 않는다.

- 로컬 `gh` 로그인으로 보이는 저장소와 웹 화면의 저장소 수가 다르면 discovery 결과·권한·affiliation을 먼저 확인하고 숫자를 강제 보정하지 않는다.
- Webhook·예약 동기화는 수동 sync의 idempotency와 운영 로그가 안정된 뒤 별도 계획으로 진행한다.
- D1 원문 용량과 쿼리 비용이 실제 사용 기준을 넘으면 source 원문만 R2로 분리한다.
- 저장소 상세 하나가 500노드 예산을 넘는 경우 Phase·상태 기반 추가 drill-down을 별도 범위로 검토한다.
- 전역 기술 엔티티 alias 품질은 실제 전체 수집 결과를 본 뒤 수동 별칭 또는 정규화 사전을 별도 계획으로 검토한다.

## 후속 그래프 UX 수정 — 자동 회전 상태 정합성

P2~P6 GitHub 수집 흐름을 완료한 뒤 별도 단일 증분으로 적용한다. 현재 `오비트` 버튼은 `궤도` 보기와 이름이 혼동되고, `prefers-reduced-motion: reduce` 환경에서 버튼만 활성화된 채 실제 `OrbitControls.autoRotate`는 비활성화되는 상태 불일치가 확인됐다.

### 구현 태스크

- [x] 연출 메뉴의 `오비트` 명칭을 실제 기능에 맞게 `자동 회전`으로 변경한다.
- [x] React 버튼 상태와 실제 `controls.autoRotate`의 유효 상태를 하나의 계약으로 동기화한다.
- [x] 모션 감소 환경에서는 자동 시작을 억제하되 사용자의 명시적 버튼 선택을 허용할지 정책을 확정한다.
- [x] 권장 정책 적용 시 `prefers-reduced-motion`은 최초 자동 실행만 차단하고, 사용자가 직접 켠 자동 회전은 낮은 속도로 동작하게 한다.
- [x] 모션 감소로 회전이 차단된 경우 버튼에 비활성 이유 또는 상태 안내를 표시해 무반응처럼 보이지 않게 한다.
- [x] `궤도` 보기와 `자동 회전` 연출을 접근성 이름·도움말·상태 요약에서 명확히 구분한다.

### 자체 테스트

- [ ] 일반 모션 환경에서 버튼 on/off에 따라 카메라 위치가 실제로 변화·정지한다.
- [x] 모션 감소 환경의 최초 진입에서 자동 회전이 시작되지 않는다.
- [x] 확정 정책에 따라 모션 감소 환경의 명시적 사용자 선택이 낮은 속도로 동작한다.
- [x] 버튼 `aria-pressed`, 활성 스타일, 실제 `controls.autoRotate` 값이 하나의 intent 계약으로 동기화된다.
- [ ] 별자리·성운·궤도 및 최대 밀도 쇼케이스에서 자동 회전 동작을 시각 검증한다.

### 증분 실행 기록 — 자동 회전 모션 감소 정합성 (2026-08-05 KST)

- `app/graph/auto-rotate.ts`에 초기 intent·사용자 토글·시스템 모션 환경 재동기화·속도·상태 텍스트를 순수 계약으로 분리했다.
- 기본 모션에서는 자동 회전이 시작되고, `prefers-reduced-motion`에서는 자동 시작을 끈다. 사용자가 `자동 회전`을 직접 누르면 상태는 활성화되고 OrbitControls는 정상 속도의 약 38%인 저속으로 회전한다.
- 사용자가 아직 조작하지 않았을 때만 시스템 모션 환경 변경에 맞춰 상태를 갱신하므로, 명시적 선택은 OS 설정 변화에 의해 임의로 뒤집히지 않는다.
- 하단 버튼의 명칭을 `자동 회전`으로 변경하고, 모션 감소 시 `감소 모션 · 자동 회전 정지` 또는 `감소 모션 · 저속 회전` 상태를 표시한다. `aria-pressed`, title, 상태 설명은 같은 intent를 사용한다.
- 검증: 모션 감소 pure contract 2개, D1 update/delete fixture, `npx tsc --noEmit`, `npm run lint`, build, `npm test` 전체 90개 통과. 실제 브라우저의 모션 감소 환경에서 초기 `aria-pressed=false`·정지 안내, 직접 클릭 뒤 `aria-pressed=true`·저속 회전 안내, 재클릭 뒤 정지 안내 복귀를 확인했다.
