이 문서는 Coreline GitHub 저장소의 `README.md`와 `dev-plan/**/*.md`를 수집·파싱해 AI Systems Atlas 지식 그래프에 적용하는 개발 범위를 고정하고, 구현이 목적 밖으로 확장되지 않도록 하기 위한 작업 문서다.

## 개발 목적

`coreline-ai` 공개 저장소의 기본 브랜치에서 루트 `README.md`와 `dev-plan` 디렉터리 아래 모든 `.md` 파일을 저장소 단위로 동기화한다. README에서는 프로젝트 목적·기능·기술을, 개발 계획에서는 Phase·작업·완료 상태·위험·의존성을 추출하고, 모든 관계가 GitHub 원문과 Markdown 블록 근거를 유지하도록 한다.

## 개발 범위

- GitHub 사용자 `coreline-ai`가 소유한 공개 저장소를 페이지네이션해 조회한다.
- 각 저장소 기본 브랜치의 루트 `README.md`와 `dev-plan/**/*.md` 일반 파일을 최소 수집 대상으로 삼는다.
- GitHub 저장소 숫자 ID와 상대 경로를 기반으로 충돌하지 않는 문서 식별자를 도입한다.
- 저장소·경로·브랜치·커밋·Blob SHA·원본 URL을 문서 메타데이터로 저장한다.
- README 전용 추출과 dev-plan 전용 Phase·체크박스 작업 추출을 기존 Markdown AST 파이프라인에 연결한다.
- 저장소 하나의 대상 문서를 모두 검증한 후에만 기존 그래프를 교체하는 저장소 단위 동기화를 구현한다.
- 모든 문서는 저장하되 그래프 화면은 전체 저장소 개요와 선택 저장소 상세의 2단계 투영을 제공한다.
- 대시보드에서 dry-run 결과, 저장소별 동기화 상태, 실패 원인, 마지막 동기화 시각과 원본 링크를 확인한다.
- 최초 전체 동기화와 이후 Blob SHA 기반 증분 동기화를 지원한다.

## 문서 기반 제약 사항

- 현재 `documents.normalized_name`은 전역 UNIQUE이므로 여러 저장소의 `README.md`가 충돌한다.
- 현재 문서 ID도 파일명에서 파생되므로 GitHub 문서에는 별도 source key 계약이 필요하다.
- 현재 일반 Markdown 추출기는 dev-plan의 Phase·체크박스 완료 상태를 구조화하지 않는다.
- 현재 업로드 API는 한 번에 최대 20개 파일이므로 GitHub 전체 동기화는 업로드 API를 우회하는 전용 서비스가 필요하다.
- 현재 성능 기준은 500노드·2,000관계이므로 전체 문서를 단일 GraphSnapshot으로 투영하지 않는다.
- 현재 공개 기본 브랜치 검색 시점의 기준치는 저장소 78개, `README.md` 77개, `dev-plan` Markdown 19개다. 실제 구현은 고정 숫자가 아니라 GitHub 응답을 정본으로 사용한다.

## 결정 기록

### 수집 대상 계약

- 포함: 저장소 루트의 정확한 경로 `README.md`
- 포함: `dev-plan/` 아래 재귀적으로 발견한 확장자 `.md` 일반 Blob
- 제외: 다른 디렉터리의 README, `.mdx`, symlink, submodule, 디렉터리 엔트리, 2MB 초과 파일
- README가 없어도 dev-plan 문서가 있으면 해당 저장소는 동기화한다.
- 재귀 Tree 응답이 `truncated=true`이면 Contents API 디렉터리 순회로 대체하고, 대체 탐색도 실패하면 해당 저장소를 변경하지 않는다.

### 식별자 계약

- 저장소 식별자: `github-repo:<github_repository_id>`
- 문서 source key: `github:<github_repository_id>:<case-sensitive-relative-path>`
- 문서 ID는 source key의 충돌 저항 해시로 만들고 브랜치·커밋 SHA를 포함하지 않는다.
- 저장소명 변경은 동일 GitHub 숫자 ID로 갱신하고, 경로 변경은 새 문서 생성과 이전 문서 stale 처리로 다룬다.
- 저장소·문서·섹션·Phase·Task 노드는 source-local ID를 사용한다.
- 언어·프레임워크·제품명·명시적 외부 링크처럼 정규화 가능한 엔티티만 저장소 간 전역 공유한다.

### 그래프 투영 계약

- `overview`: 저장소 노드와 공유 기술·명시적 저장소 간 관계를 중심으로 500노드 예산을 지킨다.
- `repository`: 선택한 저장소의 README 섹션, 계획 문서, Phase, Task와 근거 관계를 상세 투영한다.
- 추가 관계 종류는 `documents`, `plans`, `contains`로 제한하고 기존 `uses`, `requires`, `risks`, `supports`, `extends`를 재사용한다.
- 모든 규칙·Codex 관계는 document block과 GitHub source URL을 추적할 수 있어야 한다.

### 보강 계약

- 최초 전체 동기화는 규칙 기반 파싱 결과를 먼저 커밋한다.
- bulk 수집 중에는 문서별 Codex 보강 작업을 즉시 생성하지 않는다.
- 저장소 동기화 성공 후 변경 문서만 보강 큐에 넣을 수 있도록 명시적 옵션을 둔다.
- 보강 실패는 규칙 기반 그래프와 GitHub 동기화 성공을 롤백하지 않는다.

## Phase 4. 저장소 단위 원자적 동기화

### 목표

저장소의 모든 대상 문서를 먼저 다운로드·검증·파싱한 뒤 성공한 저장소만 한 단위로 적용한다.

### 구현 태스크

- [ ] manifest의 변경 Blob만 제한된 동시성으로 다운로드한다.
- [ ] repository sync stage에 문서·block·entity·mention·relation을 저장한다.
- [ ] 한 파일이라도 다운로드·검증·파싱에 실패하면 stage를 폐기하고 기존 저장소 데이터를 유지한다.
- [ ] 성공한 저장소는 create/update와 이전 manifest에서 사라진 문서 delete를 한 commit 경계에서 적용한다.
- [ ] 파일 삭제 시 다른 문서가 공유하는 전역 엔티티와 관계는 보존한다.
- [ ] 동일 Blob SHA는 파싱·보강 enqueue를 생략한다.
- [ ] bulk apply 동안 문서별 자동 보강을 억제하고 성공한 변경 문서만 후속 enqueue할 수 있게 한다.
- [ ] sync run에 discovered·changed·unchanged·deleted·failed 수와 저장소별 결과를 기록한다.
- [ ] `POST /api/github/sync/apply`와 상태 조회 API를 구현한다.
- [ ] 중복 apply 요청의 idempotency와 실행 중 충돌 방지 계약을 추가한다.

### 자체 테스트

## 잔여 리스크 / 후속 과제

- 비공개 저장소는 GitHub App 또는 fine-grained token의 Contents read 권한 설계 후 별도 계획으로 진행한다.
- Webhook·예약 동기화는 수동 sync의 idempotency와 운영 로그가 안정된 뒤 별도 계획으로 진행한다.
- D1 원문 용량과 쿼리 비용이 실제 사용 기준을 넘으면 source 원문만 R2로 분리한다.
- 저장소 상세 하나가 500노드 예산을 넘는 경우 Phase·상태 기반 추가 drill-down을 별도 범위로 검토한다.
- 전역 기술 엔티티 alias 품질은 실제 전체 수집 결과를 본 뒤 수동 별칭 또는 정규화 사전을 별도 계획으로 검토한다.
